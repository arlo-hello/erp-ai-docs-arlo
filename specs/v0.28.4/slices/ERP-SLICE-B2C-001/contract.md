- `business_outcome`: 运营可手工组合多张符合条件的待履约单；WMS 可分一个或多个包裹出库；ERP 按原 Shopify 订单商品行独立回传，部分失败可恢复。
- `blocked_by`: `[]`
- 切片类型：implementation

## 验收标准

| AC | 可观察结果 | 验证方式 |
|---|---|---|
| AC-001 | 运营可在待履约单列表跨订单选择记录；只有同店铺、归一平台客户 ID 相同、同仓库、仍可履约的记录可提交 | 归一与资格规则用 unit；服务端组合校验用 feature；主链路用 E2E |
| AC-002 | 创建组合后原 B2C/Shopify 订单及商品行保持独立，组合详情能追溯每条来源 | 聚合持久化与追溯用 feature；页面追溯用 E2E |
| AC-003 | 一个来源商品行可分配到多个实际履约单，不同原订单来源行可分配到同一实际履约单 | 分配算法用 unit；保存与读取用 feature；调整交互用 E2E |
| AC-004 | 每条来源行分配总量不超过当前可履约数量，并发提交不能超分配 | 数量守恒用 unit；事务与乐观锁冲突用 feature 并发测试 |
| AC-005 | WMS 一次或分批回传包裹时，系统只累计本次实际出库来源数量，重复回调不重复累计 | WMS explicit mock；回调幂等、部分出库和重复回调用 feature |
| AC-006 | 一张实际履约单混合多张原订单时，系统按原 Shopify 履约单及原履约商品行生成独立回传任务，并允许使用同一运单 | Shopify explicit mock；任务拆组用 unit；端到端链路用 feature |
| AC-007 | 某张原订单回传失败不回滚物理出库，不影响其他成功任务；仅失败任务可幂等重试 | Shopify 部分成功 explicit mock；补偿与幂等重试用 feature；人工重试用 E2E |
| AC-008 | 所有成员未出库时可整组取消并保留审计；任一成员已出库后，移除成员或取消组合被拒绝 | 逆向守卫用 unit；事务与审计用 feature；确认弹窗与拒绝提示用 E2E |
| AC-009 | 列表、详情、创建、调整、推送、取消、重试、导出均执行服务端权限校验，所有状态变化可审计 | 角色参数化 feature；关键角色组合用 E2E |
| AC-010 | 系统不存在本需求新增的自动合并任务；原订单的金额、支付、退款、退货和发票归属不因组合变化 | 定时任务/事件订阅负向 feature；原订单快照用 feature；边界用 explicit mock |

## 测试边界

- 独立验证声明：是

- 包含：候选资格、组合聚合、来源追溯、数量分配、并发守恒、WMS 分批出库、Shopify 分组回传、部分失败补偿、逆向守卫、权限与审计。
- 不包含：拉单自动合并、WMS 内部装箱算法、销售订单合并、支付/退款/退货/发票改造、真实 Shopify/WMS 生产联调。
- 单元测试验证归一、资格、数量守恒、状态汇总和回传拆组；feature 测试验证事务、并发、幂等、权限与审计；E2E 验证运营主链路和逆向提示。

## 依赖与 Mock 策略

- 前置切片：无；不要求其他未合入的同版本切片存在。
- WMS：显式 mock 接收实际履约单，并分别模拟单包裹、多包裹、部分出库、重复回调、乱序回调和拒绝取消。
- Shopify：显式 mock 按原履约单及商品行接收数量与运单，并分别模拟全部成功、部分成功、超时结果未知、重复请求和重试成功。
- 店铺与仓库：复用现有主数据读取契约；测试使用固定 fixture，不依赖外部网络。
- 验证顺序：unit → backend feature → frontend component → WMS/Shopify mock contract → E2E 主链路 → 逆向与并发回归。
