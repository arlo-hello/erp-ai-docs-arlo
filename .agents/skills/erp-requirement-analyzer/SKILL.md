# ERP Requirement Analyzer — 需求分析器

> 双模式引擎。目标是让需求在进入产品方案之前，经过充分的分析和结构化——避免"垃圾进、垃圾出"。

---

## 模式选择

收到需求分析任务后，先判断输入类型，选择对应模式：

| 场景 | 输入特征 | 模式 |
|------|---------|:--:|
| 用户给了 CSV 文件（飞书导出） | 结构化数据、含列名、数百行 | **Mode A** |
| 用户给了原始需求（文字/飞书文档/会议纪要） | 非结构化文本、业务语言 | **Mode B** |
| 用户既给了 CSV 又要求理解需求内容 | 先 A 后 B——CSV 质量报告 + 逐条定性解读 | **A+B** |
| 用户说"分析下需求池质量" | 明确指向质量指标 | **Mode A** |
| 用户说"整理下XX模块的需求"、"这个需求怎么理解" | 明确指向需求理解 | **Mode B** |

---

## Mode A：需求池 CSV 质量分析

> 解析飞书多维表格导出的需求池 CSV + 缺陷 CSV，产出需求质量报告。
> 关注三个核心问题：**追溯断裂**（需求↔缺陷链路）、**需求浪费**（撤回/无需处理率）、**需求结构**（类型/领域/优先级分布是否健康）。

### 前置条件

| 条件 | 说明 |
|------|------|
| 需求 CSV 存在 | 飞书导出，通常命名为 `需求及反馈管理 需求池.csv` |
| 缺陷 CSV（可选） | 飞书导出，通常命名为 `需求及反馈管理 缺陷.csv`，用于追溯率计算 |

### Mode A 工作流（3 步）

**Step A1：确认输入**

1. 询问用户 CSV 文件路径。如果用户只给了需求 CSV，询问是否有缺陷 CSV（追溯率分析需要，无则跳过）。
2. 如果用户提及目录，自动搜索 `*需求池*.csv` 和 `*缺陷*.csv`。

**Step A2：运行分析脚本**

```bash
python3 .Codex/skills/erp-requirement-analyzer/scripts/analyze_requirements.py <需求CSV路径> [缺陷CSV路径]
```

脚本输出 JSON 到 stdout。核心指标：

| 指标 | 说明 | 健康阈值 |
|------|------|:--:|
| `traceability_rate` | 需求关联缺陷的百分比 | ≥ 30% |
| `waste_rate` | 撤回+无需处理的需求占比 | ≤ 10% |
| `type_withdrawal` | 各需求类型的撤回率 | 单项 ≤ 15% |

**Step A3：生成需求质量报告**

按模板输出 Markdown 报告，保存到 `docs/tech/requirement-analysis-{模块}-{日期}.md`。

完整报告模板见下方「Mode A 输出模板」。

### Mode A 输出模板

```markdown

> 分析时间: {ISO8601} | 需求数: {N} | 缺陷数: {M}

|------|--------|--------|:--:|
```

### Mode A 关键指标解读

**追溯率为什么重要**：低追溯率意味着大量缺陷无法追溯到源头需求 → 不知道哪些需求质量差 → 无法针对性改进需求评审。

**浪费率为什么重要**：高浪费率意味着大量需求投入最终被撤回或废弃。综合需求和需求评估通常是重灾区。

**类型分布为什么重要**：某些类型（如"综合需求"）占比过高且缺乏明确定义边界，应拆分。

## Mode B：原始需求定性分析

> 对非结构化的原始业务需求进行解读、抽象、结构化，产出可直接作为产品方案输入的需求分析文档。
> 这不是产品方案本身——它回答的是"做什么、为什么、影响谁"，而不是"怎么做、页面长什么样"。

### Mode B 工作流（5 步）

**Step B1：需求接收与理解**

1. 确认输入来源：文字描述 / 飞书文档 / 会议纪要 / 用户反馈 / 多个来源混合
2. 如果有飞书文档链接，先用 `feishu-doc-downloader` 拉取内容
3. 通读全部原始材料，提取核心诉求
4. 识别模糊点：主动向用户提问澄清。典型的待澄清问题：
   - "XX 功能的应用场景是什么？哪些角色会用？"
   - "XX 和现有 YY 功能的关系是什么？是替代还是补充？"
   - "优先级如何？有没有隐含的分期假设？"

**Step B2：多维度分析**

从 6 个维度审视需求：

| 维度 | 检查点 | 产出 |
|------|---------|------|
| **完整性** | 覆盖了哪些环节？缺什么？ | 缺口清单 |
| **清晰度** | 核心概念定义是否明确？是否有歧义？ | 待澄清项 |
| **可行性** | 技术可行？现有系统能否支撑？ | 可行性评估 |
| **一致性** | 与现有功能是否冲突？与业务规则是否矛盾？ | 冲突点 |
| **可测试性** | 验收标准是否明确？如何验证？ | 验收要点 |
| **可追溯性** | 需求来源是否清楚？优先级是否有依据？ | 来源追溯 |

**Step B3：跨域影响评估**

对照 ERP 10 大领域模型，评估需求影响范围：

| 域 | 缩写 | 检查问题 |
|------|------|---------|
| 商品域 | PRODUCT | SKU 主数据需要新增字段吗？ |
| 平台域 | PLAT | 渠道/店铺配置需要变更吗？ |
| 订单域 | ORDER | 订单流程需要调整吗？ |
| 物流域 | LOGIS | 入库/出库/履约流程需要变更吗？ |
| 库存域 | IMS | 库存结构（表/维度）需要变更吗？ |
| 售后域 | ASS | 退货/换货/退款流程受影响吗？ |
| 支付域 | PAY | 收款/退款/对账受影响吗？ |
| 财务域 | FIN | 结算/分账/报表受影响吗？ |
| 采购域 | PUR | 采购单/供应商流程需要调整吗？ |
| 通用域 | COMM | 需要新审批流/通知/文件吗？ |

> 详细领域模型参考 `.context/constitution/DDD_DOMAIN_MODEL.md` 和 `.context/modules/`。

**Step B4：风险识别**

主动识别以下风险类型：

| 风险类型 | 检查点 |
|---------|---------|
| 数据一致性 | 多系统（ERP-WMS）数据同步是否有断层？ |
| 兼容性 | 与现有功能是否冲突？旧数据如何迁移？ |
| 边界模糊 | 功能边界是否清晰？是否隐含了范围膨胀？ |
| 角色缺失 | 是否遗漏了某类用户的使用场景？ |
| 过渡期 | 系统上线前的过渡期如何运作？ |

**Step B5：产出结构化文档**

根据需求复杂度选择产出物：

| 复杂度 | 产出物 | 位置 |
|--------|--------|------|
| 简单（单域、<5 功能点） | 一份需求分析报告 | `docs/requirements/{module}/01-requirement-analysis.md` |
| 中等（跨域、5-15 功能点） | 需求分析报告 + 业务需求文档 | `01-requirement-analysis.md` + `02-business-requirements.md` |
| 复杂（跨 3+ 域、15+ 功能点） | 需求分析 + 业务需求 + 需求规格 | 三份完整文档 |

### Mode B 输出文档结构

> 详细模板见 `references/mode-b-templates.md`。核心结构如下：

**01-requirement-analysis.md** 包含：
1. 需求范围（包含/不包含——明确边界比列功能更重要）
2. 核心设计决策（为什么这样设计，决策依据是什么）
3. 全单据影响范围（入库/出库/库存/查询/采购... 逐类分析）
4. DDL 变更清单（哪些表需要加字段、改索引）
5. 关键决策记录（决策+结论+原因，供后续评审追溯）

**02-business-requirements.md** 包含：
1. 业务背景与痛点（用表格呈现，每个痛点配业务影响）
2. 功能范围（包含/不包含）
3. 详细需求（按模块展开，每个模块含字段表、流程图、核心规则）
4. 特殊场景（如中转仓、过渡期等边界场景）
5. 角色与场景
6. 业务规则汇总（编号列表，供测试用例生成直接使用）
7. 术语表

### Mode B 核心原则

1. **边界优先**：先定义「不做什么」再列「做什么」——防止范围膨胀
2. **决策透明**：每个设计选择都要写清楚「为什么」——方便后续评审追溯
3. **跨域视角**：不只看主域，还要看对其他域的涟漪效应
4. **可测试性**：业务规则用编号列表呈现——方便 `test-case-generator` 直接引用
5. **增量清晰**：如果有多个版本迭代，标注版本间增量变更

## 边界情况

| 情况 | 策略 |
|------|------|
| Mode A：缺缺陷 CSV | 跳过追溯率、缺陷密度分析，报告中标注"缺缺陷数据" |
| Mode A：CSV 列名与预期不符 | 打印实际列名，参考 `references/csv-columns.md` 对照 |
| Mode A：数据量为 0 | 🛑 提示检查文件是否为空 |
| Mode A：中文字段乱码 | 确认文件编码为 UTF-8，飞书导出默认 UTF-8 BOM |
| Mode B：用户需求很模糊 | 不猜测，主动提问澄清；用 Step B1 的待澄清问题清单 |
| Mode B：需求涉及多模块 | 先侦察现有代码（调用 `erp-scout-protocol`），确保影响面分析基于真实代码 |
| Mode B：需求与现有功能冲突 | 在风险清单中标注冲突点，给出兼容方案或替代方案 |
| Mode B：用户只给了口头描述 | 先用文字整理理解，请用户确认后再进入分析 |
| A+B 模式：数据与内容脱节 | CSV 中的需求与用户描述的痛点不一致时，标注差异并确认 |

## 关联技能

| 技能 | 触发时机 | 关系 |
|------|---------|------|
| `erp-scout-protocol` | Mode B Step B3 前必须执行 | **前置依赖**——影响面分析基于真实代码 |
| `external-design-miner` | Mode B 分析完成后，需要行业对标时 | 下游——搜索行业最佳实践 |
| `erp-product-doc-generator` | 需求分析完成后，进入产品方案阶段 | **直接下游**——Mode B 产出是其输入 |
| `erp-pipeline-orchestrator` | 一键启动全流程时 | 编排器将本技能作为第 ⓪ 步调用 |
| `feishu-doc-downloader` | Mode B 输入为飞书文档时 | 上游——拉取飞书文档内容 |
| `test-case-generator` | 需求中的业务规则需要转化为测试用例时 | 下游——Mode B 的业务规则汇总表可直接作为测试输入 |

## 兜底约束

1. **不修改原始输入**：CSV 只读分析，飞书文档不修改原文
2. **脱敏处理**：报告中敏感信息（人名、邮箱）脱敏
3. **错误透明**：脚本出错时输出原始错误信息，帮助用户修正格式
4. **输出位置**：
   - Mode A → `docs/tech/requirement-analysis-{模块}-{日期}.md`
   - Mode B → `docs/requirements/{module}/01-requirement-analysis.md`（及其他文档）
5. **侦察先行**：Mode B 涉及代码影响面分析时，必须先调用 `erp-scout-protocol`
6. **不替代产品方案**：Mode B 产出是需求分析，不是产品方案。不要生成页面线框图、UI 描述、路由设计——那是 `erp-product-doc-generator` 的职责
