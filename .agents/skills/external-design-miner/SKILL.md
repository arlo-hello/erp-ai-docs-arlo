# External Design Miner — 外部设计挖掘器

> 通过联网搜索和 GitHub 搜索，为产品设计提供行业对标和方案参考。

---

## 触发时机

- 用户说"搜索一下XX功能的最佳实践"
- 用户说"业界通常怎么做XX"、"竞品是怎么设计XX的"
- 用户说"GitHub上有没有类似的XX系统设计"
- `erp-product-doc-generator` 在 Stage 0.5 自动调用
- 任何产品方案设计前需要外部参考的场景

---

## 核心流程（三步）

```
需求关键词
  │
  ▼
Step 1: 多源搜索
  ├── 联网搜索（WebSearch）：技术博客、产品文档、竞品分析
  └── GitHub 搜索（gh CLI）：开源仓库、Issue、PR、README
  │
  ▼
Step 2: 提炼萃取
  ├── 自动摘要：每条结果 1-2 句核心设计点
  ├── 模式识别：反复出现的术语/数据模型/交互模式
  └── 差异分析：对比项目现状，标注可直接借鉴 vs 需适配
  │
  ▼
Step 3: 输出报告 → 《设计参考报告》
```

---

## Step 1：多源搜索

### 1.1 搜索关键词生成

根据需求描述，生成 3-5 组搜索关键词。关键词组合策略：

| 维度 | 关键词模板 | 示例 |
|------|-----------|------|
| 功能+最佳实践 | `{功能名} 最佳实践 系统设计` | `采购退货 仓库选择 最佳实践` |
| 英文技术搜索 | `{功能名英文} design pattern best practice` | `purchase return warehouse selection design` |
| 竞品搜索 | `{竞品名/领域} {功能名} 怎么设计` | `ERP 退货单 仓库 设计` |
| 数据模型搜索 | `{功能名} database schema design` | `purchase order payment plan db schema` |
| UI 交互搜索 | `{功能名} UI UX interaction pattern` | `credit note deduction UI pattern` |

### 1.2 联网搜索（使用 WebSearch + WebFetch）

```
1. 使用 WebSearch 工具搜索每关键词，取前 5 条结果
2. 对有价值的 URL 使用 WebFetch 获取详情
3. 搜索优先级：技术博客 > 产品文档 > 问答平台 > 百科
4. 自动过滤：排除纯广告、低质量采集站、无实质内容的页面
```

### 1.3 GitHub 搜索（使用 gh CLI）

```
1. 仓库搜索:
   gh search repos "{关键词}" --sort stars --limit 5
   关注：README 中的架构图、数据库 Schema、API 设计

2. Issue 搜索（设计讨论）:
   gh search issues "{关键词} design" --limit 5
   关注：Issue 中的需求讨论、方案对比、决策理由

3. Wiki/讨论区搜索:
   gh api "search/code?q={关键词}+in:file+language:markdown" --jq '.items[:5]'
   关注：.md 文件中的设计文档、数据库 ER 图、流程图描述

4. 筛选标准：
   - Star >= 50 的仓库优先
   - 最近 2 年有更新的仓库优先
   - 包含 README/文档的仓库优先
```

### 1.4 搜索约束

| 约束项 | 规则 |
|--------|------|
| 最大搜索次数 | 每关键词 1 次搜索，总计 ≤ 10 次搜索调用 |
| 最大 Fetch 次数 | 只 Fetch 最有价值的 ≤ 5 个 URL |
| 时效性权重 | 2 年以内的信息权重最高，超过 2 年的降低权重并标注 |
| 安全边界 | 仅读取公开信息，不上传任何项目代码或数据 |

## Step 2：提炼萃取

### 2.1 自动摘要

对每个被 Fetch 的页面或 GitHub 仓库，生成 JSON 摘要：

```json
{
  "source": {
    "url": "https://example.com/erp-design",
    "title": "ERP系统采购退货模块设计",
    "type": "技术博客",
    "date": "2025-08",
    "credibility": "high"
  },
  "summary": "该文章描述了退货单与仓库的多对一关系设计，建议在下拉框中展示仓库容量和当前负载",
  "key_design_points": [
    "仓库选择下拉框支持搜索联想（>100个仓库时）",
    "退货单创建时实时查询仓库容量，超过80%告警",
    "退货入库自动匹配最近有该商品出库记录的仓库"
  ],
  "applicability": {
    "direct": ["仓库下拉搜索组件"],
    "adapted": ["仓库容量预览（需对接库存模块API）"],
    "skip": ["自动匹配仓库（与现有手动选择流程冲突）"]
  }
}
```

### 2.2 模式识别

从 3+ 个独立来源中识别反复出现的模式：

```
识别规则：
├── 同一术语出现在 ≥3 个来源 → 标记为「行业通用术语」
├── 同一交互模式出现在 ≥2 个来源 → 标记为「常见交互模式」
├── 同一数据模型出现在 ≥2 个来源 → 标记为「参考数据模型」
└── 来源为头部公司/知名项目 → 提升权重
```

### 2.3 差异分析

对照项目自身的领域模型（从 `.context/constitution/DDD_DOMAIN_MODEL.md` 读取），标注：

| 外部模式 | 项目现状 | 差异 | 建议 |
|---------|---------|------|------|
| 仓库容量实时查询 | 仓库选择下拉框为静态列表 | 缺少容量预览 | 建议在退货弹窗增加「仓库容量」字段（只读） |
| CN抵扣自动按到期日排序 | 已实现（CN-C04规则） | 无差异 | 无需变更，仅作为正确性验证 |
| ... | ... | ... | ... |

## 护栏规则（红线）

| # | 规则 | 说明 |
|---|------|------|
| 1 | **每条引用必须可追溯** | 所有外部参考附带来源 URL，自检时逐条验证 |
| 2 | **不提交项目代码到外部** | 搜索时只使用公开关键词，不上传代码片段或 Schema |
| 3 | **明确标注来源时效** | 超过 2 年的信息标注 `[已过时]`，仅作参考 |
| 4 | **不直接复制设计** | 提取通用模式，不复制具体的 UI 布局/代码/文档段落 |
| 5 | **人工审核为最终决策** | 所有外部参考在进入 PRD 前须人工确认 |
| 6 | **搜索结果上限** | 每次调用总计 ≤ 10 次搜索 + ≤ 5 次 Fetch，避免过度消耗 |

## 与 erp-product-doc-generator 的集成

```
erp-product-doc-generator 流水线：
  Stage 0: 需求解析
  Stage 0.5: 行业对标 → 调用 external-design-miner → 输出 design-reference-report.md
  Stage 1: 产品方案生成 → 结合现状 + 设计参考报告 → PRD
```

**调用方式**：erp-product-doc-generator 在 Stage 0.5 中将需求关键词传递给 external-design-miner，读回 `design-reference-report.md`，在 Stage 1 中以「设计参考」段落融入 PRD。

---

## 关联技能

- `erp-product-doc-generator` — 产品方案生成器（调用方）
- `erp-scout-protocol` — 代码侦察（提供项目现状对照）
- `frontend-doc-generator` / `backend-doc-generator` — 也可独立调用本 Skill 获取设计参考
