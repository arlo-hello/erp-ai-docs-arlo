# ERP 产品方案文档生成器

> 基于 PMP × 敏捷 × DDD × 五层设计体系，将需求分析到交付定义为七个 AI 可执行技能。主文件为编排器，每个技能的完整指令按需从 `references/` 加载。

**核心逻辑**：事件定义I/O → 影响性评估过滤 → 链路基于I/O串联 → 模块高内聚归类 → 功能多层级设计 → PRD整合 → 切片发现与契约产出。

**产物三层规则** 🔴：
1. **分析账本**：`领域事件清单.md` ~ `功能设计说明.md` 保持系统分析过程，完整性、逐行计数、状态组合、守恒校验和追溯 ID 不降级。
2. **读者交付**：`产品需求文档.md` 与 `产品系统设计方案.md` 面向评审读者重组信息，结论先行、责任清楚、大表有解释；执行前必须 Read `references/readability-standard.md`。
3. **追溯附录**：引用前校验、完整大矩阵、事件/功能/页面/切片/风险/缺口映射放附录或独立 Trace Ledger。正文只保留决策所需的摘要和关键例外，不丢原始追溯。

**三个锚点词贯穿全链**（每个词触发同一种行为模式，每次出现都预判同样的处理方式）：
- `sanity-check` — 每步产出后自问「这个结论的证据在哪？」。不声明"已通过"，只信填表结果和逐行对照。
- `combinatorial` — 实体有多维度状态时，正面穷举所有组合格。一个维度变，整个矩阵重过。
- `symmetry` — 每个正向操作追问逆向、每个新增追问涟漪、每个加追问减、**每个 N:1 聚合追问成员取消（全取消/全禁止二选一：全部未执行下一步→全取消后重建；任一已执行下一步→禁止取消。禁止中间方案）**。成对检查，不成对=漏设计。

## 全局约束

> 以下约束横切全部七个技能。

| # | 约束 | 说明 |
|:---|:---|:---|
| 1 | **侦察先行** | 技能5深读每个 Model 的完整字段/枚举/关联/方法，标注「已有/部分/全新」 |
| 2 | **纯中文** | 产品方案全文使用中文业务术语，不出现代码路径、类名、API 端点 |
| 3 | **I/O 驱动串联** | 上游事件的输出 = 下游事件的输入，链路本质是 I/O 有序组合 |
| 4 | **需求→系统对照** | 需求驱动模式，技能5先输出对照表再做功能设计 |
| 5 | **输入类型判断** | 启动前判断：需求文档(需求驱动) vs 模块名(代码驱动) vs 无文档(追问索要) |
| 6 | **线框优先** | 技能5每个关键页面输出 ASCII 线框图（列表页+详情页），技能6 PRD引用 |
| 7 | **字段语义消歧** | 两个语义相近的字段必须显式说明差异 |
| 8 | **概念关系显式化** | 涉及多个关联实体时用「核心概念关系」章节说明 |
| 9 | 🔴 **功能完整性** | 方案必须保证功能完整闭环。不进行功能分期。所有连锁事件必须追踪到末端并产出对应功能点和切片。技能间传递必须带数量校验——下游产出数 ≥ 上游事件数 |
| 10 | 🔴 **表格逐行完整** | 每行独立填写完整业务内容。每个事件/功能/切片都是独立实体，必须独立描述。表格不压缩为一行摘要，不跨行引用"同XX""同上""同前"等——每行是独立实体，占独立行 |
| 11 | 🔴 **事实分级** | 技能1先登记事实与来源，确定性只允许：已确认 / 可推断 / 未确认 / 未询问。技能2对未确认、未询问、矛盾事实执行缺口三问（范围 / 时间 / go-no-go） |
| 12 | 🔴 **命名分层** | 技能1术语注册表输出架构稳定名、业务对象名、产品能力名、端侧展示名。产品层业务名优先，稳定名放括号；命名不得改变域边界、稳定 ID、对象归属和生命周期 |

### 输入类型判断

```
用户提供了什么？
├── 需求文档（.md / 飞书链接 / PDF / 多个文件）
│   → 需求驱动模式：走完整七技能
├── 只提供了模块名 / 无需求文档
│   → 代码驱动模式：从代码侦察开始，逆向生成（不编造需求）
└── 用户说"按需求做XX"但未提供文档
    → 🔴 追问索要需求文档，不猜测需求内容
```

**代码驱动模式的特殊处理**：

| 差异点 | 需求驱动模式 | 代码驱动模式 |
|:---|:---|:---|
| 技能1「需求来源」列 | 引用需求文档段落（如 `需求§5: "..."`） | 标注 `代码逆向推导: {文件路径}:{行号}` |
| 技能5 需求→系统对照表 | 对照需求文档规则 | 对照"系统现状"（侦察结论充当基线） |
| 技能2 影响性基线 | 以需求文档为基线 | 以「现有系统行为」为基线，变更 = 偏差 |
| 编造限制 | 需求未提及 → 不列入 | 代码未实现 → 标注"该模块尚未实现"，不编造 |

### 边界情况

| 情况 | 策略 |
|------|------|
| 模块代码不存在 | 标注"该模块尚未实现"，不编造 |
| 字段含义无法推断 | 标注"待确认"，不猜测 |
| 用户跳技能触发 | 检查前置技能产出是否存在 |
| 需求文档与代码冲突 | 以需求文档为准，标注偏差 |

## 整体流程

```
技能1:事件 → 技能2:影响性&可行性 → 技能3:链路 → 技能4:模块 → 技能5:功能 → 技能6:产品方案 → 技能7:切片发现
                                                                                                    ↓
                                                                                     技能8:汇总方案（七技能完成后执行）
```

- 每个技能的输出是下一个技能的输入。
- **渐进式加载**：触发时只加载本编排器。执行技能N前，Read `references/skill-N-xxx.md` 获取完整指令。
- **技能8为汇总步骤**：不参与验证门流转，在七技能全部完成后执行。将前序所有产出整合为一份自包含的《产品系统设计方案》，用于与开发团队评审。

## 技能间验证门

> 双重保障：① **输入契约**（输入不齐不启动）事前约束；② **验证门**（完成后回溯）事后兜底。
> **验证门 vs 技能内检查清单**：验证门（本表）是权威关卡——决定能否进入下一技能。各 reference 文件中的「完成后验证」清单是执行指南——帮助 AI 在执行过程中自检。两者目标一致但粒度不同：验证门关注跨技能一致性（计数传递、链路覆盖），技能内清单关注本技能产出完整性（维度覆盖、格式合规）。验证门不通过 → 回溯；技能内清单不通过 → 当场修正。
> **口径权威**：各技能的输出字段、维度定义和示例以对应 reference 为权威；本表只检查跨技能传递和一致性，不重复维护字段定义。
> 🔴 **术语一致性横切门**（②→③~⑦→① 所有验证门通用）：每道门附加问「🔴 **术语一致性**：本技能产出中所有术语是否与技能1注册表一致，无变体（如技能1注册"调拨单"则下游不准出现"预报调拨入库单"替换"调拨单"）？不一致 ≠ 升级写法，是信息链断裂——回本技能统一术语」。这是投入最小、防实战翻车最狠的校验。

## 技能概要

> 以下为每个技能的简要定位。执行前必须 Read 对应参考文件获取完整指令（思考步骤、输出格式、质量标准、完成后验证）。

### 技能1：事件穷举与输入输出定义

**一句话**：穷举所有业务事件，用11维 I/O 表定义每个事件的输入输出，并逐行携带Fact ID、状态敏感性和自动化决策。

**核心规则**：7种事件类型（人的操作-单个/批量/逆向、系统触发、系统触发-连锁、系统触发-补偿、外部回调）；连锁事件必须独立列出，追踪到状态不再变更。🔴 **每个事件标注状态敏感性**——输出随前置状态变化的（如已发货预报vs未发货预报）须按前置状态拆成独立分支行。🔴 **事实清单标注确定性**（已确认/可推断/未确认/未询问）。🔴 **语义相近术语填命名理由和四层命名**。🔴 **MECE 互斥性**（事件无重复/重叠/歧义）。🔴 **外部回调与连锁事件做时序/幂等/并发分析**（重复回调、乱序到达、并发操作）。

**产出**：领域事件清单（含11维 I/O、Fact ID/状态敏感/自动化决策治理列；影响性标记初始为空，技能2回写）。

> 🔴 **执行前必须 Read `references/skill-1-events.md`——不Read直接执行将导致事件漏穷举、连锁未追踪、术语未注册。** 摘要只是索引，完整指令在参考文件中。

### 技能2：影响性与可行性分析

**一句话**：13维度评估（9影响+4可行），决定做不做、怎么做，并保持本期功能完整闭环。

**核心规则**：结论回写——每个事件标注🟢本期实现或🔴本期不做（附阻塞理由）。不做功能分期。📖 `references/skill-2-impact.md`
**新增判断链**：缺口三问（范围/时间/go-no-go）+ PM判断链（假设、证据类型、成功指标、竞争路径、结论）。📖 `references/skill-2-impact.md`

**产出**：影响性分析表 + 可行性分析表 + 结论 + 事件标记回写。

> 🔴 **执行前必须 Read `references/skill-2-impact.md`。**

### 技能3：业务链路串联

**一句话**：先画用户故事地图（用户视角完整性），再画双视图泳道（跨域数据流），每个节点标注单据三元组。

### 写作策略 🔴

> 以下规则把金字塔原理翻译为 AI 可执行的写作约束。

1. **结论先行**：每一章开头用加粗一句话给出该章的结论（如"采购域负责采购下单到入库预报的全流程，对内采链和调拨链只做触发判定、不做执行"），后面再展开细节。
2. **以上统下**：段落首句为论点，剩余句为论据。先给结论再展开。
3. **归类分组**：同一领域的设计（流程/单据/状态/接口）聚在一章内——开发者按域阅读时不应跳章。一章覆盖一个域的完整设计。
4. **逻辑递进**：领域章节内部按“责任边界→领域职责→单据→流程→状态机→标准规则→接口→数据”递进，这是开发者理解一个域的认知顺序。
5. **引用做摘要，不做照搬**：每个前序产出引用时提取关键信息重述，不复制大段原文。技能6 PRD 是产品视角，本文件是系统设计视角，共享概念用不同写作层次（PRD偏"为什么"、本文件偏"怎么做"）。
6. **自包含**：读者无需翻阅其他文件即可理解完整设计。
7. **读者密度**：默认每章达到3段论证或1表/图+1段解释；简单章节允许短写或合并，但必须标注密度降级原因，禁止凑密度。
8. **表格解释**：大表之前说明这张表回答什么问题，之后给2-3条关键takeaway；超过6列或15行的完整矩阵移附录。
9. **命名表达**：产品层业务名优先，架构稳定名放括号；能力名为动作+对象+可感知结果；页面名为端侧任务化短名；切片名为业务结果名。

### 图表标准 🔴

> 🔴 **Mermaid/ASCII 图表必须在技能3和技能5生成时就遵循兼容语法，技能8不做语法转换（语法转换是治标，源头规范才是治本）。** 技能3和技能5在产出图表时即遵守以下规则，技能8直接引用：

- Mermaid序列图：不使用 `actor`（用 `participant`），不使用 `-->>` 虚线（用 `->>` 实线）
- Mermaid流转图：不使用 `-.->` 虚线过渡（用 `-->`）
- Mermaid状态图：状态名不使用中文+下划线（如`未预报_未发货`），使用短ID（如`s00`）+ `note`标注中文语义
- ASCII框图：使用 `+` `|` `-` 字符（不使用box-drawing字符 `┌└├─`）
- 特殊字符（`≠` `≥` `≤`）改用中文表述（"不等于""大于等于""小于等于"）
- ASCII单据关系图：横向超过4个节点的改用树形缩进结构

### 需求变更处理

1. 评估变更影响——从哪个技能的输入开始受影响。
2. 回溯到该技能重新执行，告知用户「因需求变更，从技能X重新分析」。
3. 下游产物标记为「待重新生成」。

### 输入不齐时的处理

如果用户跳技能触发但前置产物不存在，告知用户并提供选择：从缺失技能开始完整执行 / 用户提供替代输入。
