# ERP-182 需求分析：Shopify 跨订单组合发货

> 四位任务号：`0182`  
> Multica Issue：`ERP-182`  
> 分析模式：Mode B  
> 需求来源：Issue 描述、评论 `01a1a0a4-5ae0-74cb-aa37-d6d9f59c8b0b`、评论 `01a1a0ce-365e-7bea-b385-34aa01de1d55`、评论 `01a1a492-20d2-7b95-a0a6-d217c7c47d17`

## 1. 结论

本期有条件能做。范围是运营人员手工选择多张 Shopify 原订单的待履约单，建立组合发货关系；原 B2C 订单、Shopify 订单、商品行、金额和售后归属不改变。组合可拆成一个或多个实际履约单及物理包裹，出库后按原 Shopify 履约商品行分别回传数量，同一物理包裹的运单允许回传到多张原订单。（来源：评论 `01a1a492-20d2-7b95-a0a6-d217c7c47d17` Q1、Q5）

本期不实现拉单时自动合并，不使用“同一天”作为系统自动判定规则，不把多张原订单合成一张销售订单。（来源：评论 `01a1a492-20d2-7b95-a0a6-d217c7c47d17` Q1、Q4、Q5）

| 决策 | 结论 | 来源 | 影响域 |

| D-01 触发方式 | 运营手工选择跨订单履约单合并 | Q1 | B2C 订单、权限、审计 |

| D-05 结果模型 | 原订单独立；新增组合发货关系；物理包裹可一或多；按原商品行回传 | Q5 | B2C、WMS、Shopify |

设计树 frontier 已为空；Q1-Q5 均为 `settled`。通知策略不改变数据归属与状态模型，默认沿用 Shopify 每张原订单的通知行为，若业务要求抑制通知则作为平台配置评审项，不阻塞本切片。（来源：Q5 对话及 Q1-Q5 最终答复）

## 3. 范围

### 3.1 包含

1. 运营人员从待履约单列表批量选择跨订单记录并发起组合。（来源：Q1）
2. 服务端校验同店铺、归一后的平台客户 ID 相同、仓库相同、记录仍可履约。（来源：Q2、Q3；仓库与待履约限制来自现有合并能力的代码事实）
3. 新增组合发货主关系、来源商品行分配关系、实际履约单映射关系。（来源：Q5）
4. 允许一个来源商品行拆到多个实际履约单，允许一个实际履约单包含多张来源订单商品行。（来源：Q5 场景说明）
5. WMS 一次或分批出库后，按来源 Shopify 履约单及商品行生成独立回传任务。（来源：Q5）
6. 同一物理包裹运单可出现在多张原 Shopify 订单的回传中。（来源：Q5）
7. 组合、拆分、取消、出库回传和失败重试均记录审计。（来源：手工合并的责任可追溯要求；属于可推断系统约束）

### 3.2 不包含

1. 拉单后自动发现或自动创建组合。（来源：Q1、Q4）
2. 合并 B2C 销售订单、支付、金额、发票、退款或售后主体。（来源：Q5“原订单保持独立”）
3. 用姓名、电话、邮箱或地址替代平台客户 ID 判等。（来源：Q3）
4. 修改 WMS 内部装箱算法；ERP 只接收实际包裹、运单和出库数量。（来源：Q5“WMS 可形成一个或多个物理包裹”）
5. 已发生实际出库后从组合中单独移除成员。（来源：组合关系的来源守恒与不可逆要求，可推断）

## 4. 现状侦察与差异

| 维度 | 已有能力 | 新需求 | 差异判断 |
|---|---|---|---|
| 履约归属 | 履约单通过 `order_no` 归属单一订单；履约明细归属单一订单商品行 | 一个发货编排可承载多张原订单商品行 | 全新组合关系，不能复用单一归属表达 |
| 合并 | 仅允许同一 `order_no`、同仓库、待履约状态的两张履约单 | 跨订单手工组合 | 现有合并不可直接放开 |
| 拆分 | 可按 Shopify 履约商品行 ID 与数量拆分 | 跨订单组合后继续拆成多个实际履约单 | 可复用行级数量思想，需保留来源映射 |
| Shopify 回传 | 以 Shopify 履约单 ID 发起回传，并落商品行回传标识 | 一次物理出库可能拆成多张原订单的回传 | 需新增按来源分组的回传任务与幂等状态 |
| 页面入口 | 现有操作围绕单订单详情 | 待履约列表跨订单批量选择 | 新增列表批量入口和组合详情 |

## 6. 数据变更建议

| 对象 | 关键字段 | 用途 |
|---|---|---|
| 组合发货 | 组合编号、店铺、归一平台客户 ID、状态、创建人、版本号 | 手工组合的聚合根与并发控制 |
| 组合来源行 | 组合编号、原订单号、原订单商品行、Shopify 履约单 ID、Shopify 履约商品行 ID、可履约数量 | 永久保存交易来源 |
| 履约分配 | 组合来源行、实际履约单、分配数量 | 同时表达合单和拆单 |
| 平台回传任务 | 实际履约单、原 Shopify 履约单、来源行、数量、运单、幂等键、状态、重试次数 | 隔离仓库出库与平台回传状态 |

DDL 由技术方案确定最终表名与索引；产品不指定物理命名。必须有唯一幂等键、来源行数量校验、组合版本号和软删除/审计字段。

## 7. 风险与可行性

| 风险 | 等级 | 触发条件 | 应对 |
|---|---|---|---|
| 平台客户 ID 归一误匹配 | 高 | 大小写、前缀或空白处理不一致 | 明确归一算法；原值与归一值同时审计；空值禁止组合 |
| 并发超分配 | 高 | 两人同时组合或拆分同一来源行 | 行级锁或乐观锁；提交时重算可履约数量 |
| 出库成功而部分平台回传失败 | 高 | 多张原订单中部分 API 失败 | 出库不回滚；按来源任务幂等重试；展示部分失败 |
| 组合成员取消 | 高 | 已组合后原订单取消或退款 | 未出库时整组取消后重建；任一成员已出库后禁止移除并转人工异常处理 |
| 相同运单多订单通知 | 中 | Shopify 对每张订单发送通知 | 默认按平台原订单通知；是否抑制由平台能力另行评审 |

技术可行性：有条件可行，需新增关系模型和回传任务，不能只改校验。业务可行性：已确认手工触发与数据归属。时间可行性：需技术评估后排期。依赖可行性：WMS 可通过明确出库回调 mock 独立验证，Shopify 可通过接口 mock 验证分组与幂等。
