# ERP-190 组合履约需求分析

## 1. 输入锚点

| Fact ID | 来源 | 原文事实/已确认决策 |
|---|---|---|
| F-001 | Issue 需求背景 | Shopify 短时间内可能产生同店铺多张订单，ERP 当前按 1:1 生成 B2C 订单并分别推仓。 |
| F-002 | Issue 边界 1 | Shopify 无法调整，ERP 合并后 Shopify 仍是多张原单。 |
| F-003 | Issue 边界 1 | 必须覆盖履约、取消履约、挂起、取消挂起、退款、更新运单、取消、推仓、拆分履约、更换仓库。 |
| F-004 | Issue 边界 2 | 必须定义上游原单操作对组合对象、组合对象对下游单据的影响。 |
| F-005 | Q1 确认 | 保留原履约单，新增仓库执行聚合层。 |
| F-006 | Q2 确认 | 本期仅支持用户手动勾选合并，不做自动候选池或定时自动合并。 |
| F-007 | Q3 确认 | 同项目、同店铺、同收件人、标准化地址、国家、币种、仓库、库区、物流渠道、贸易条款且未推仓、未挂起、无异常才可合并。 |
| F-008 | Q4/Q7 确认 | 未推仓可重建；仓库已接单未出库须先整单取消；已出库不改写发运事实，退款按原订单行处理。 |
| F-009 | Q5/Q6 确认 | 一张物理包裹共享一个运单号；各 Shopify 原单分别按自己的 fulfillment order 回写；发运状态与平台同步状态分离。 |
| F-010 | Q5 现状补充 | 原履约单生成时即存在 1:1 初始化出库流水。 |
| F-011 | Q8 确认 | 业务名称统一为“组合履约单”；它是唯一推仓主体，新出库流水只是库存域执行凭证。 |

## 2. 问题与目标

当前一张 Shopify 原单、一张 B2C 订单、一张原履约单和一张初始化出库流水形成独立链路（F-001、F-010）。线下仓库会把多个包裹人工合并，但 ERP 无稳定的 N:1 发运对象，导致推仓、库存、运单回传和平台同步的事实不一致（F-001、F-004）。

本期目标是让操作员把符合严格条件的多张未推仓履约单组合为一个仓库执行单元；保留每张上游原单的身份、商品行和售后归属，同时只向仓库推送一次（F-002、F-005、F-006、F-007）。

## 3. 范围

### 本期包含

- 履约单列表多选、组合资格校验、预览和确认（F-006、F-007）。
- 组合履约单及成员关系、唯一出库流水、库存释放与重新占用（F-010、F-011）。
- 组合推仓、挂起/取消挂起、取消、更新运单、仓库出库回传（F-003）。
- 原单取消、退款、拆分、更换仓库对组合关系的重建规则（F-003、F-008）。
- 仓库出库后按成员分别同步 Shopify，并对失败成员幂等重试（F-009）。
- 全链路审计、异常提示、权限与并发保护（F-004）。

### 本期不包含

- 自动识别候选、等待窗口、定时自动组合（F-006）。
- 修改 Shopify 单据模型或将多张 Shopify 原单合成一张（F-002）。
- 已出库后的拆包、撤销发运或局部改写仓库事实（F-008）。

## 4. Open Decisions Closed

| 决策 | 结论 | 来源 | 影响域 |
|---|---|---|---|
| 聚合模型 | 保留原履约单，新增组合履约单 | F-005 | B2C、IMS、Shopify、WMS |
| 触发方式 | 人工多选，不自动组合 | F-006 | 前端、任务调度 |
| 资格 | 严格同构且未推仓 | F-007 | 校验、物流、库存 |
| 逆向 | 下一执行阶段前可重建；已出库只做售后 | F-008 | 状态机、补偿 |
| 运单 | 物理包裹共享运单，各原单独立回写商品范围 | F-009 | Shopify、客户通知 |
| 库存凭证 | 取消原流水并释放，再创建唯一新流水并占用 | F-010、F-011 | IMS、库存守恒 |
| 业务命名 | 统一称“组合履约单” | F-011 | 页面、API、日志 |

## 5. 可行性与影响

| 维度 | 判断 | 依据 |
|---|---|---|
| 业务价值 | 高：减少仓库侧人工并单和重复推仓 | F-001 |
| 用户影响 | 中：新增多选组合及组合单详情；原单仍可查 | F-005、F-006 |
| 数据影响 | 高：新增聚合根、成员映射和同步结果 | F-004、F-009 |
| 库存影响 | 高：必须事务化保持释放量与重占量相等 | F-010、F-011 |
| 外部系统 | 高：WMS 一次推送，Shopify 多次独立回写 | F-002、F-009 |
| 可逆性 | 推仓前可解组；接单后需取消成功；出库后不可逆 | F-008 |
| 技术可行性 | 可行：新增聚合层，不破坏原履约单归属 | F-005 |
| 运营可行性 | 可行：人工选择降低误合并，但需清晰失败原因 | F-006、F-007 |

结论：Go。前提是组合事务、库存守恒、并发锁、WMS 幂等键和 Shopify 成员级同步结果全部进入验收范围；缺少任一项不得上线。

## 6. DDL 变更清单（产品级）

| 对象 | 用途 | 关键数据 |
|---|---|---|
| 组合履约单 | 仓库执行聚合根 | 组合单号、项目、店铺、仓库、物流、发运状态、平台同步汇总状态、版本号 |
| 组合履约成员 | N:1 映射与规则快照 | 组合单号、原履约单号、原订单号、原出库流水号、商品/数量快照、同步状态、失败原因 |
| 组合操作日志 | 审计和补偿追踪 | 操作、前后状态、操作者、请求幂等键、外部请求号、结果 |

物理表名、索引名和字段类型由技术方案确定；必须对成员履约单建立“同一时刻至多属于一个有效组合”的唯一约束。
