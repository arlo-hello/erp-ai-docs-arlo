# ERP-192 需求分析

> 任务号：0192  
> Multica Issue：ERP-192  
> 分析模式：Mode B  
> 当前状态：待业务决策，尚未进入产品方案与切片定义

## 1. 原始需求锚点

| 来源 ID | 原始需求段落 |
|---|---|
| RQ-BG | 背景现状：不同供应商或仓库的采购单需要分开下单，但工厂可能合并发货、合并入库；采购入库单需包含完整发货数据，保证采购、内采、销售、调拨链路正确。 |
| RQ-1 | 发货列表勾选供应商不同但仓库一致的采购发货单，合并预报，只生成一张采购入库单。 |
| RQ-2 | 预报成功后，按实际预报数据修改各发货单预报状态。 |
| RQ-3 | 一张采购入库单可关联多张发货单，详情页展示全部关联发货单。 |
| RQ-4 | 多张发货单可能来自多个采购单；仅当所有采购主体唯一且一致时展示目的主体所属系统、目的主体、中转，否则隐藏。 |
| RQ-5 | 确认入库、取消入库保持原逻辑；原先关联单张发货单的逻辑扩展至多张。 |
| RQ-6 | 补全勾选多个采购订单生成一张采购入库单的上下游边界。 |
| RQ-C1 | 第一轮业务确认：Q1、Q2 与推荐答案一致；Q3 待业务确认；Q4 要求先核实现有供应商展示逻辑，运费采用本次合并预报填写的整票货运信息；Q5 支持跨分页选择，任一筛选条件变化时清空，提交时后端重新校验。 |

## 2. 一页结论

该需求技术上可行，但不是把 `shipping_no` 从字符串改成数组即可完成。现有入库明细关系表已经逐行保存采购单号、发货单号和采购明细，可以作为多发货单追溯事实源；单据头、接口校验、并发锁、发货状态校验、取消回滚、详情资源和前端路由均仍以单个发货单号为中心，必须统一扩展。[RQ-1][RQ-2][RQ-3][RQ-5]

建议采用“入库单头不再以单一发货单作为权威关系，关联关系以入库明细关系表为准”的兼容方案：保留旧字段供历史数据读取，新增或明确单据级多发货关联查询；所有状态计算按每张发货单各自的已预报数量重新聚合，不允许用整张入库单统一覆盖状态。[RQ-2][RQ-3]

当前不能进入产品方案与切片 `DEFINED/READY`：多张发货单的可选状态、整单确认门槛和跨分页选择规则已经确认；同 SKU 不同价格/核算维度的合并口径仍待业务确认。Q4 的运费口径已确认，但代码复核证明现状不是“第一条商品行供应商”，多发货单下如何确定唯一展示供应商仍需一次收口确认。这些决策直接改变验收标准、数据结构和回滚链。[RQ-5][RQ-6][RQ-C1]

## 8. 风险与可行性

| 等级 | 风险 | 证据与影响 | 缓解建议 |
|---|---|---|---|
| 高 | 并发重复占用 | 当前锁只使用一个发货单号（F-02）；两个集合交叉时会重复增加 `inbound_num`。 | 集合内单号排序后逐单加锁；事务内再次校验剩余量。 |
| 高 | 成本与主体串线 | 当前入库商品行可聚合同 SKU，但成本与主体来自明细关系（F-03、F-06）。 | 采用 Q3 推荐粒度，所有确认/取消按关系分摊。 |
| 高 | 整单确认绕过未发货单 | 当前只检查单头单号（F-05）。 | 按关联发货单集合校验全部已发货并返回阻断清单。 |
| 中 | 详情唯一供应商取值不稳定 | 当前供应商来自单头唯一发货单，不是第一商品行（F-08）；多发货单若改取第一行而没有固定排序，同一单据可能展示不同供应商。 | 业务确认唯一展示口径后，在接口层固定商品排序和供应商取值规则；发货单数组仍完整返回。 |
| 中 | 取消后状态不一致 | 当前单头逻辑只重算一个发货单（F-07）。 | 从关系表取受影响发货单集合并逐单重算。 |
| 中 | 中转字段仅前端隐藏 | 当前 UI 会清空字段，但请求仍允许任意提交（F-10）。 | 后端按采购主体集合强校验，多主体提交中转字段直接拒绝。 |

可行性结论：数据关系基础可复用，后端、前端和测试均需变更；预计无需为“入库—发货”关系新增独立表，但需通过后续技术方案确认是否为查询性能增加组合索引。该结论不等同于 DDL 最终结论。[RQ-1][RQ-3][RQ-6]
